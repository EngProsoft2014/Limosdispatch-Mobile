Startup session routing
=======================
The initial window uses StartupPage.xaml and StartupViewModel, not LoginPage.
SessionRestoreService renews expired tokens and validates the current profile
and company before opening the role-specific tab workspace. LoginPage is
created only when a session is absent/rejected or password change is required.
Temporary network/server failures preserve the saved session and offer Retry.

Remember me still controls persistence across app restarts. Explicit sign-out
clears session tokens, so remembering credentials does not undo a sign-out.
Startup does not submit or rewrite the saved password.

46 automated core checks passed. New checks cover valid/expired sessions,
administrator/chauffeur restoration, explicit sign-out, rejected renewal,
company mismatch and retaining sessions during temporary failures.
Android build/run and iOS managed compilation passed. The Android emulator
reopened directly into Rides using the existing saved session.

Active-session validation (10 November 2026)
------------------------------------------
The added SessionMonitorService and its 20-second polling timer were removed
at the user's request. There is no separate periodic session-validation request
or monitor startup/resume hook. Startup session restoration and normal API
requests retain their existing authentication checks.

The normal API path attempts refresh after a 401. Rejected refresh credentials
or a second 401 with the renewed access token clear the secure session and
raise SignedOut. A delayed rejection of an older token cannot clear a newer
login. Network errors, timeouts, 403 on a resource, and 5xx preserve the session.
Authentication rejection does not remove offline synchronization data.

The backend must invalidate the old session on another device's login and
reject its access token at /api/auth/me (not only when its JWT expires), as
well as reject its refresh token. A client cannot enforce cross-device session
exclusivity if the backend still accepts both sessions.

The documented driver SignalR hub currently exposes TripAssigned; no server
session-revocation event/payload is present in the supplied API contract.
No event names or push payloads have been assumed. Immediate event-driven
logout needs the backend's actual hub/event contract. Push delivery alone
cannot guarantee that a suspended/killed iOS application executes logout;
normal authenticated API requests detect rejection when they are sent.
